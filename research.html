The problem

An infected camera still looks like a camera.

Connected devices commonly ship with default passwords and rarely get updates. Botnet malware such as Mirai and Gafgyt (also called Bashlite) logs in, installs itself, and turns the device into one node of a botnet. From then on it scans for the next victim and floods targets on command.

The owner notices nothing. The camera keeps streaming. The only visible change is in its network traffic: who it talks to, how often, and how much.

The device can't defend itself. It has too little memory and processing power to run a model, and it is the thing that has been compromised.

The one place that sees every connection is the gateway: the home router, an IoT hub, or a network tap. That is where a detector like ours would run.

The study

Three models, trained on traffic from real infected devices.

We compared three supervised models: a CNN, a 1D CNN, and a hybrid CNN-RNN, where convolution layers extract features and recurrent layers model them as a sequence. Each had to label a traffic record as benign or as a specific botnet attack.

The main dataset was N-BaIoT (Meidan et al., 2018): traffic from real IoT devices infected with Mirai and Gafgyt, summarised as 115 statistical features per record. A second dataset, NSL-KDD, checked that the chosen model generalises beyond it.

CNN-RNN, batch size 256. Overall accuracy looked fine, but it hid two failures.

Per-class report 0 recall

Mirai UDP was never caught: recall 0. Gafgyt TCP had a precision of 0.54, so almost half of what the model called Gafgyt TCP was something else. Mixing TCP and UDP traffic confused the model, so we removed TCP.

The paper builds a detector. It does not block traffic, capture packets live, or deploy anything. Those are the questions the last two sections take on.

    Re-examined

    Re-examined, three years on.

    A result is only as good as the test behind it. In November 2026 I re-ran the public notebook and scored it on NSL-KDD's official test file, KDDTest+, instead of a random slice of its own training file. The gap between those two numbers is the most useful thing this project taught me.

    99.5% → 76.6%

    Random splits flatter the model.

    The notebook scores 99.49% on a random 20% of its training file and averaged 76.6% on KDDTest+ across three seeds. NSL-KDD contains many near-identical rows. A random 20% split puts near-twins of training rows into the test set, so the score mostly measures how well the model remembers.

    0.8% → 12.2%

    The test file has a different mix.

    R2L attacks, where an outsider gains access to a machine, are 0.8% of the training data and 12.2% of the test file. The model rarely saw them, so it rarely catches them: R2L recall was about 10% in the 3-seed re-run.

    17

    A closed set can't name what's new.

    The softmax output must choose one of the 23 labels it trained on. Faced with one of the 17 attack types missing from training, it can only guess the nearest familiar label, or call it normal.

    A random split of the training file answers an easier question than the one a deployed detector faces. Knowing that difference is the job.

    From paper to product

    Where the model would sit in a real network.

    This kind of model scores a finished connection: its duration, its byte counts, how it ended. So it runs out of band, next to the traffic rather than in its path, and its output is an alert that leads to action on the device's next connections.

    1. Gateway

      Router, IoT gateway or network tap. Sees every connection; the devices are too weak to run a model.

    2. Flow records

      One record per finished connection, for example Zeek's conn.log.

    3. Feature service

      Computes the rolling-window statistics the model expects, such as recent connections to the same host.

    4. Model service

      About 2 ms per connection on a laptop CPU, model only. The paper's part.

    5. SIEM

      Alerts land beside every other security signal.

    6. Review

      A person or a second signal confirms before anything is cut off.

    7. Quarantine

      Firewall rule or VLAN move for the device's next connections.

    Because the score arrives after the connection ends, the model cannot block the connection it is scoring. It can only stop the device's next ones.

    The base-rate problem

    A small false-positive rate on a large number of connections still produces a flood of false alerts. Move the sliders to see it. Recall and the default false-positive rate are fixed at the 3-seed re-run's 64.5% and 7.4%, close to the demo model's figures above.

    What would make it shippable

    In order
    1. Split N-BaIoT by device, so no device appears in both training and test.
    2. Evaluate on unseen devices and unseen attacks, and report those numbers first.
    3. Calibrate thresholds on the target network's own benign traffic, to set the false-positive rate it can afford.
    4. Save the model and its preprocessing together, so the scaler and category encodings can't drift apart.
    5. Run in log-only shadow mode first, measuring alerts against what analysts confirm.
    6. Add anomaly detection for attacks never seen in training, alongside the classifier.
